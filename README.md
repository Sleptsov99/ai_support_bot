# AI Support Bot: движок, вторая итерация

Веб-сервис бота поддержки AvaBet (Uplatform), интегрированный с чатом Consultant через webhook + REST API.
Python 3.11+, FastAPI. LLM спрятан за интерфейсом: есть адаптер Claude (`core/claude_llm.py`) и офлайн-заглушка
на ключевых словах (`FakeLLM` / `DemoLLM`), поэтому всё запускается и тестируется без сети и ключей.

Правки по результатам теста (25 пунктов из документа правок + таблица методов оплаты по гео):

* **L1 и оператор**: сразу на L1 только явная зависимость или самоисключение; жалоба на проигрыш, «это скам» и
  «пополнить, чтобы отыграться?» бот ведет сам (ответственная игра). Пока ждем ответ о времени, L1 только после
  3 сообщений подряд без ответа; молчание не повод. Бот никогда не обещает оператора: кнопки «оператор» вырезаются,
  фраза «соединю / передам» ловится фактчеком и переписывается.
* **Время платежа**: модель только извлекает, что сказал клиент (дата, «вчера», день недели, час, часть дня), а часы
  считает код в часовом поясе гео (`core/timeparse.py`). «Вчера вечером», дата без часа: бот уточняет час, если
  выходит около 24 ч. Без гео спрашивает, сколько часов прошло. Срок депозита везде «до 24 часов», без точного часа.
* **Сбор данных > 24 ч**: максимум 4 вопроса: способ (кнопки методов гео из `data/payment_methods.json`), сумма и время
  одним вопросом, кошелек, чек из кошелька (депозит) или скриншот заявки из истории AvaBet (вывод). Номер получателя
  и телефон не спрашиваются. Чек переспрашивается один раз, потом передача без него, в карточке L1 это видно.
* **Кнопки**: приветствие получает приветствие и 3 кнопки; дальше 12 категорий → 6 популярных запросов → 3-4
  вероятных от модели. «Неуспешный платеж» сначала уточняется (ошибка или списались). Номер счета без текста
  распознается. «Да / нет» продолжают текущую проблему.
* **Текст**: без markdown, вопрос отдельным абзацем, у сообщения о передаче нет вопроса в конце, арабским клиентам
  support-ar@, справочник контактов в базе. База: верификация до 24 ч, агенты через @payment_assistment_avabet_bot,
  единый ответ про лимиты.

Что изменилось во второй итерации (по замечаниям Кирилла):

* **Эскалация**: попытка считается только по сигналу неудачи (не помогло / не понял / повтор / недоволен /
  просьба оператора), как размечено в эталонных диалогах. Ответы на уточняющие вопросы идут как прогресс,
  поэтому длинный продуктивный диалог больше не уходит на L1. Счётчики ведутся по каждой проблеме отдельно.
* **Корнер кейсы**: шум («сэр», «?») и оффтоп не считаются попытками и не эскалируются. Агрессия задаёт тон
  ответа и не меняет тему. Риск (лудомания, суицидальные мысли) даёт бережный ответ и сразу L1. Срок оплаты
  понимается как диапазон: на «вчера» бот один раз переспрашивает. Если больше 24 ч, бот собирает данные для
  L1 как в диалоге 4. Если клиент молчит после вопроса о сроке, таймер передаёт диалог на L1.
* **Контекст**: сообщения склеиваются с адаптивным окном. Если клиент дописал, пока бот думает, ответ
  пересчитывается заново и попытка не засчитывается дважды. История чата читается из Consultant: после
  рестарта контекст восстанавливается, а если в чат написал живой оператор, бот замолкает.
* **Живые ответы**: Claude пишет каждый ответ сам, от лица персоны. Вся база знаний одним документом лежит в
  кешированном префиксе вместе с эталонными диалогами. Перед отправкой фактчек: числа и ссылки должны быть в
  базе, нет фраз «я проверил платёж» и запрещённых слов. При ошибке одна переделка, потом ответ из базы как есть.
* **Языки**: сильные языки модель обрабатывает сама, слабые (sw, am, zu, ky, af) идут через перевод на английский, см. ниже. Язык диалога меняется только по
  уверенному определению («ok» или «40 min» его не переключают).

## Запуск

Нужен Python 3.11+ (на маке системный 3.9 не подойдет: `brew install python@3.12`).

```bash
python3.12 -m venv .venv && . .venv/bin/activate
pip install --upgrade pip
pip install -r requirements.txt   # или: pip install -e ".[dev]"
pytest -q                         # 93 теста, без сети
```

### Демо в браузере

```bash
python -m support_bot.demo                         # заглушка, без ключа: http://127.0.0.1:8000/demo
ANTHROPIC_API_KEY=sk-... python -m support_bot.demo # тот же движок на Claude
```

Слева чат-виджет как у Consultant. Справа данные клиента и состояние движка: персона, тема, группа,
сигнал последнего сообщения, неудачные попытки и счётчики по проблемам, данные, собранные для L1, причина
передачи. Там же все JSON, которые уходят в Consultant. Сценарии для показа:

1. «сэр» → «сэр ?» → «какая погода»: уточнение, короткий пинок, возврат к теме; счётчики не растут.
2. «не могу войти» → «не помогло» ×5 → шестая неудача: эскалация с заметкой для L1 (SupportBotMessage → прощание → InvokeOperator).
3. «депозит не пришел» → «вчера» → «часов 5 назад»: переспрос около 24 ч, потом стандартный срок без эскалации.
4. «депозит не пришел» → «уже 3 дня» → способ, чек, сумма, время, номера: сбор данных и L1 (диалог 4). «Я уже всё отправил!» один раз объясняется, второй раз уходит на L1.
5. «проиграл все, не могу остановиться»: бережный ответ и сразу L1.

С заглушкой тексты шаблонные (ru/en), база тестовая из 7 ответов (`support_bot/demo/demo_kb.json`).

### Проверка на живой модели: 4 пользовательских сценария

```bash
pip install -r requirements.txt
DEEPSEEK_API_KEY=sk-... python scripts/try_cases.py        # или ANTHROPIC_API_KEY=... для Claude
DEEPSEEK_API_KEY=sk-... python scripts/try_cases.py 3      # только третий сценарий
```

Гоняет весь движок (вебхук → диспетчер → движок → реакции Consultant) на настоящей базе `data/kb.md`, языки по схеме ниже. Для каждого хода печатает, что написал клиент, как бот его прочитал (для языков с переводом),
что клиент получил, кнопки, заметку для L1 и время ответа. Сценарии:

1. Египет, арабский диалект: депозит через Vodafone Cash не пришёл, прошёл час, клиент просит человека → обычный срок, без эскалации.
2. Кения, суахили: забыл пароль → ответ из базы на суахили; «всё равно не работает, SMS не приходит» → следующая попытка.
3. Нигерия, английский: депозит со вчерашнего утра → сбор данных → раздражение → передача на L1 с карточкой.
4. Эфиопия, амхарский (через перевод): как вывести деньги, пошагово.

### Языки: сильные сами, слабые через английский

Так делают Intercom Fin и другие: база на одном языке (у нас русский), модель сама читает вопрос клиента и
отвечает на его языке. Исследования (IrokoBench) показывают, что перевод помогает только там, где модель слаба:
для африканских и редких языков перевод на английский заметно поднимает качество, для сильных моделей и
языков разницы нет, а лишний перевод стоит двух вызовов модели и стирает тон персоны и диалект.

Поэтому по умолчанию `PIVOT_LANGUAGES=sw,am,zu,ky,af`, `PIVOT_TARGET=en`: эти языки идут через перевод на
английский (вопрос → английский → ответ из русской базы по-английски → перевод на язык клиента), остальные
(en, ar, fr, es, ru, tr, az...) модель обрабатывает сама. `PIVOT_LANGUAGES=*` + `PIVOT_TARGET=ru` — всё через
русский; `PIVOT_LANGUAGES=""` — без перевода. Сравнить режимы: `python scripts/try_cases.py --compare`.
Протокол прогона на DeepSeek: `docs/deepseek_run.txt`.

### Боевой режим

```bash
CONSULTANT_BOT_TOKEN=... ANTHROPIC_API_KEY=... KB_PATH=support_bot/data/kb.md \
  uvicorn support_bot.app:create_app --factory --port 8000
```

Webhook: `POST /webhook` (или `/webhook/<WEBHOOK_SECRET>`). Все переменные окружения с дефолтами описаны в
шапке `support_bot/app.py`. Основные: модели `CLAUDE_ANALYZE_MODEL` / `CLAUDE_COMPOSE_MODEL` (по умолчанию
`claude-opus-5-5`), `LLM_PROVIDER=deepseek` + `DEEPSEEK_API_KEY` (модель `deepseek-chat`), `PIVOT_LANGUAGES`, `PAYMENT_SILENCE_SECONDS` (0, выкл.), `BOT_MARKDOWN` (0), `CONTACT_MEMORY_HOURS` (0, выкл.),
`RISK_ESCALATES` (1).

### База знаний

`support_bot/data/kb.md` собрана из таблицы «ТЗ бот основные блоки вопросы/ответы» (лист «NEW ТЗ Итог»,
исходник лежит рядом: `data/qa_source.xlsx`). 530 вопросов → 242 ответа: формулировки одного вопроса с одним
ответом склеены в `variants`, статус / условие / эскалация из таблицы лежат в строке `note:` (только для бота),
подсказки «Может быть вы искали это» из листа «ТЗ по подсказкам по блокам» добавлены в каждый раздел.
Размер ~37k токенов, целиком уходит в кешированный префикс промпта.

Обновить после правок таблицы:

```bash
pip install openpyxl
# Файл → Скачать → .xlsx (CSV/gviz теряют строки, свёрнутые в группы)
python scripts/qa_to_doc.py qa.xlsx -o support_bot/data/kb.md
```

Ответы в таблице на русском; бот отвечает на языке клиента, сохраняя шаги, названия разделов, контакты и цифры.

## Как устроено

```
Consultant --POST /webhook--> app.py --(200, пустое тело сразу)
                                 |
                                 v
                           dispatcher.py   очередь на chatId, адаптивная склейка, пересчёт при дописывании,
                                 |         история чата из Consultant, таймер тишины, Ping -> Pong
                                 v
                        core/engine.py     детерминированная политика по ТЗ (run_turn -> commit)
                 /        |          |          \            \
     core/llm.py     core/guard.py  core/state.py  core/budget.py  core/translation.py
     (протокол,      (фактчек)      (стейт по      (14.6, доля     (режим переводчика
      FakeLLM)                       проблемам)     эскалаций)       по языкам)
     core/claude_llm.py + core/prompts.py (кешированный префикс: правила + KB + эталонные диалоги)
                                 |
                                 v
              consultant/adapter.py -> consultant/client.py -> POST /bot/{token}/messages
```

Один ход:

1. **analyze** (LLM, строгий JSON): язык и уверенность, тема, сигнал (прогресс / не помогло / не понял / повтор /
   недоволен / шум / завершение), оператор, платёж и срок диапазоном, тон, жалоба, оффтоп, риск, данные платежа.
2. **политика** (код): какая проблема, считать ли неудачу, группа A/B/D, сбор данных, эскалация.
3. **compose** (LLM): текст от лица персоны под задачу и номер попытки, плюс кнопки.
4. **guard**: фактчек, при ошибке одна переделка, потом ответ из базы как есть.
5. Перевод обратно (только для языков в режиме переводчика), отправка.

Модель ничего не решает про эскалацию: она только классифицирует, а решение принимает код. Его можно
протестировать, и ТЗ выполняется детерминированно.

## Открытые вопросы (дефолты уже реализованы, переключаются конфигом)

1. Клиент молчит после вопроса о сроке: по правкам теста молчание не повод для L1, таймер выключен (`PAYMENT_SILENCE_SECONDS=0`).
2. Явная зависимость, просьба о самоисключении и суицидальные мысли: сразу L1 (`RISK_ESCALATES`). Жалобы на проигрыш и «отыграться» бот ведет сам.
3. Заметка о прошлом обращении на 48 ч выключена (`CONTACT_MEMORY_HOURS=0`). ТЗ стейт между сессиями не требует.
4. Как в истории Consultant отличить сообщения бота от оператора: сейчас по совпадению текста. Нужен ответ Uplatform.
5. Расхождения таблицы с ТЗ (см. ниже), пока везде действует ТЗ.

### Где таблица расходится с ТЗ (сейчас работает по ТЗ)

* «Два аккаунта», «подозреваю взлом», «аккаунт заморожен» помечены «Вызов оператора»; по ТЗ сразу на L1 только платёж > 24 ч.
* «3 нераспознанных подряд → эскалация»; по ТЗ 5 неудачных попыток.
* Поддерживаемые языки RU/EN/AR/FR/ES; в ТЗ 12 языков.
* Ответы на жалобы обещают «передаю специалисту», хотя эскалации не происходит: бот эту фразу не повторяет, пока движок реально не передаёт диалог.
* Приветствие в таблице сразу от персоны; по ТЗ первое сообщение на английском без имени, персона представляется после определения GEO.

## Чего пока нет

1. Обработка изображений (по договорённости не для первого релиза); файл в сборе данных просто прикладывается к заметке.
2. Персональные данные: номера и суммы сейчас попадают в заметку L1 как есть.
3. Хранилище: стейт и бюджет эскалаций в памяти процесса; для нескольких инстансов нужен Redis (`DialogueStore`, `EscalationBudget`).
